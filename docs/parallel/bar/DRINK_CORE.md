# Ядро напитков: модель и проверочный стакан

DRINK-CORE-01, 2026-10-27. Первый реализованный этап [плана](DRINKS_PLAN.md). Отдельные RefCounted-модели, без зависимости от сцены бара, дома, Session или файлов сохранений. В основной игре пока остаётся существующее меню подачи; новый состав ещё не передаётся гостю.

## Попробовать

В Godot 4.7.2 открыть `tests/parallel/bar/drink_lab.tscn` и запустить текущую сцену F6. Или `godot --path . res://tests/parallel/bar/drink_lab.tscn`.

Выбрать TEST-сосуд, дозу и темп. Для трёх слоёв: включить «Слоем», темп 5, налить плотный компонент → базовый → лёгкий. Для шота взять по 20 мл, для большого стакана можно по 40. «Перемешать» разрушает границы совместимых компонентов; «Встряхнуть» также объединяет отдельные фазы; «Дать отстояться» разделяет группы смешивания. «Слить» удаляет сверху выбранный объём. «Зафиксировать результат» запечатывает состав, «Новый стакан» создаёт независимую порцию. Это отдельный TEST-стенд с условными цветами и параметрами, не финальный интерфейс или арт бара.

## Каталог

`scripts/service/drinks/drink_material_catalog.gd`, DrinkMaterialCatalog. `load_file(path: String) -> bool`, `load_document(data: Variant) -> bool`; `is_loaded/is_test_content() -> bool`, `get_ingredient_ids/get_vessel_ids() -> PackedStringArray`, `get_ingredient/get_vessel(id: StringName) -> Dictionary`. Неизвестный ID возвращает пустой словарь. validation_errors — диагностические сообщения.

JSON v1: ровно schema_version=1, test_content bool, ingredients и vessels. Материал: id/title, density, viscosity, color[4], strength, taste{sweet,sour,bitter}, mix_group, tags[]. Сосуд: id/title/capacity_ml. ID ASCII snake_case до 64 символов, заголовок непустой до 160. Числа конечные и не bool; плотность >0..10, вязкость/крепость/цвет/вкус 0..1, вместимость >0..2000 мл. До 128 материалов/32 сосудов, файл до 256 КиБ, уникальные ID/теги, неизвестные/отсутствующие поля отклоняются. Все определения проверяются до принятия; неудачная загрузка не оставляет частичный каталог. После успеха каталог не перезагружается, исходные/полученные словари независимы.

Текущие данные только `tests/parallel/bar/drink_materials.json`: шесть вымышленных TEST-материалов, две вместимости 60/240 мл. Данные не утверждают реальные рецепты/ингредиенты мира. Теги добавок — только метаданные состава, никаких биологических/сюжетных эффектов этот модуль не применяет.

## Стакан и команды

`scripts/service/drinks/drink_preparation.gd`, DrinkPreparation. `configure(catalog: DrinkMaterialCatalog,vessel_id: StringName,preparation_id: StringName) -> bool` один раз, копирует определения. Внешний владелец обязан выдавать уникальный preparation_id для каждой реальной порции; ядро не хранит глобальный реестр порций. Смена сосуда означает новый экземпляр.

- `pour(command_id,ingredient_id: StringName,volume_ml: float,flow_ml_s: float=10,layered: bool=false) -> bool`.
- `mix(command_id: StringName,method: StringName=&"stir") -> bool`: stir или shake.
- `settle(command_id: StringName) -> bool` — явное отстаивание без течения реальных секунд.
- `discard(command_id: StringName,volume_ml: float) -> bool` — слив сверху, смесь в одном слое удаляется пропорционально.
- `seal(command_id: StringName) -> Dictionary` — финальный снимок или пустой словарь при отклонении.
- `get_snapshot/get_result() -> Dictionary`, `get_volume_ml() -> float`. До configure снимок пустой; get_result пустой до seal.

Каждый command_id уникален внутри порции и среди всех типов операций; невалидная команда его не занимает. Повтор успешной команды отклоняется без эффекта. Переполнение/неизвестный материал/неправильный темп/нечисловое состояние/пустое смешивание не меняют состав. Минимальная доза 0,001 мл, темп >0..500 в условных единицах мл/с. Для погрешности double допускается обрезка до остатка вместимости/объёма в пределах 0,000001 мл; в журнале команды сохраняются requested_volume_ml и фактический volume_ml. Это не частичный налив при настоящем переполнении.

Журнал ограничен 4096 обычными командами, финальный seal зарезервирован сверх лимита, чтобы не блокировать завершение порции. revision равен числу принятых команд. После seal все изменения отклоняются; повторный seal не создаёт второе событие. get_result возвращает независимую копию с event_id=`drink:<preparation_id>:<command_id>`. Это результат приготовления, не событие уже совершённой подачи GuestService: доставку и идемпотентность на уровне гостя подключает следующий этап.

## Условная модель слоёв

Слои хранятся снизу вверх, каждый — фактические объёмы компонентов. Их плотность/вязкость/цвет/крепость/вкус вычисляются по объёмным долям. Общий профиль вычисляется по всему составу; теги сортируются и объединяются, не теряются при смешивании. Цвет — только простая смесь для визуального прототипа, не оптическая симуляция.

Осторожный налив сохраняет границу, если входящий компонент легче верхнего хотя бы на 0,02 и темп не выше `8 + 32 * viscosity_верхнего_слоя`. Числа являются параметрами игровой модели для TEST, не физической калибровкой. Превышение темпа, неправильный порядок или обычный налив объединяют совместимые материалы. Плотный компонент поверх лёгкого не сортируется автоматически в идеальные цветные слои.

Одинаковая mix_group означает полную совместимость в этой модели. Разные группы остаются отдельными фазами при обычном наливе/перемешивании и располагаются по плотности; при равенстве используется стабильный порядок ID группы. Shake объединяет все группы в условную эмульсию, последующий налив сохраняет её. Settle снова разделяет группы; слои одной совместимой группы при отстаивании также объединяются. Автоматического старения, температуры/льда/растворения/химических реакций нет на этом этапе. Эти правила явно упрощены и могут настраиваться после игровых проб.

## Снимок и дальнейшие потребители

get_snapshot содержит schema_version=1 (версия runtime-контракта, не checkpoint), test_content, preparation_id, vessel, sealed, revision, structure (empty/homogeneous/layered/emulsified), overall, layers и operations. В профиле/слое: volume_ml, components{id:ml}, density/viscosity/strength/color/taste/tags и emulsified. Журнал операций хранит их порядок/способ/дозировку/исход укладки: одинаковый итоговый состав не теряет различия технологии приготовления.

Все getters/результаты — глубокие копии. Состояние порции остаётся в памяти; сериализация/загрузка и новая схема сохранений не введены. Кандидаты будущих потребителей: распознавание рецепта, представление стакана, адаптер подачи, реакции гостя. Пока реальные потребители — два теста и TEST-стенд. Контракты Main/GuestService/NarrativeSession/Home/Journal не менялись.

## Проверки и следующий шаг

`tools/check_drink_core.ps1 -Godot <движок>` импортирует проект, запускает drink_core_test.gd и drink_lab_test.gd. `-Graphics` добавляет 1280×720/960×600 и снимки слоёв/смеси; создаёт отдельную папку artifacts/drink-core-*. Проверяет exit code, ошибки движка и обязательный PASS-маркер. Отдельная команда ядра: `godot --headless --path . --script res://tests/parallel/bar/drink_core_test.gd`.

Общий runner намеренно не меняется в параллельной дорожке. При интеграции координатор добавит новый профиль и при необходимости лабораторию в Validation, а TEST-стенд оставит вне игрового пути. Следующий конкретный этап — каталог рецептов/допусков и распознавание состава/технологии; затем уже заменить выбор готового напитка действиями у рабочей стойки. Реакции гостей ждут интеграции неизменяемого результата, а не чтения цвета стакана/текста UI.
