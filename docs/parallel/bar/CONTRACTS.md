# DA-060: изменённые контракты и потребители

## WORKBENCH-04: независимые смеси и техники, 2026-10-27

Основание — BARTENDING_RESEARCH.md с профессиональными источниками/разделением фактов и коэффициентов. Прежнее требование ложки WORKBENCH-02 заменено: ложка расширяет допуск, очень мягкий низкий налив у стенки тоже допускает слой. Главный критерий — плотность выходящей смеси и энергия струи.

DrinkPreparation добавляет:

- `pour_blend(command_id: StringName, components: Dictionary, flow_ml_s: float=10, layered: bool=false) -> bool`: входящая смесь одной дозой; проверка всех известных положительных конечных компонентов и общей вместимости до мутации, плотность/вязкость всей смеси. Погрешность <=EPS обрезается до фактического свободного места. Повторные дозы того же соотношения продлевают один верхний слой.
- `transfer_to(command_id: StringName, target: DrinkPreparation, volume_ml: float, flow_ml_s: float=10, layered: bool=false) -> Dictionary`: атомарная проверка обеих моделей/ID/составов определений/вместимости; self/null/запечатанный/недоступный источник или получатель отклоняются. Возвращает {volume_ml,components} фактической дозы или {}. Удаление сверху, внутри слоя — пропорционально. Фиксирует transfer_out у донора и transfer_in у получателя одним ID внутри каждой модели. В журнале входа — source, components, volume_ml, layered/outcome, source_technique до извлечения и переданное dilution_ml. При отказе обе модели и ID сохраняются. Лёд не переносится; несмешанные отдельные фазы не превращаются в эмульсию только от перелива, настоящая shake-эмульсия сохраняется.
- `extract(command_id, volume_ml) -> Dictionary`: те же фактические volume_ml/components без получателя; для пролива. `get_free_space_ml() -> float` учитывает жидкость и оставшийся лёд.
- `add_ice(command_id: StringName, volume_ml: float=40) -> bool`: требует материал test_water и свободное место, хранит водный эквивалент льда. `empty_container(command_id) -> bool`: удаляет жидкость/лёд, сбрасывает текущую технику, оставляет историю с событием очистки. Пустой/запечатанный/невалидный запрос без эффекта.
- `mix(command_id,method,duration_s: float=1) -> bool` — прежние первые два аргумента, новый необязательный положительный конечный duration_s<=60. Stir/shake различаются аэрацией/условной мощностью работы со льдом. Таяние добавляет реальный test_water, сохраняет liquid+ice, меняет крепость/вкус. Без льда нет охлаждения/разбавления. Shake с тегом test_carbonated атомарно отклоняется; stir разрешён.
- `get_vessel/get_technique/get_view() -> Dictionary`: независимые лёгкие копии для UI без растущего журнала. get_view содержит vessel/structure/overall/layers/technique, не operations. Полный get_snapshot/get_result сохраняет прежние поля runtime v1 и аддитивное поле technique{ice_ml,temperature_c,dilution_ml,aeration,stirred_s,shaken_s}. Это не новая схема checkpoint. При переливе температура/аэрация усредняются по фактическому объёму, талая вода переносится по её реальным компонентам даже из слоистой порции; stirred_s/shaken_s отражают максимальную обработку пришедших смесей, не сумму повторных доз. Точная температура каждого отдельного слоя пока не моделируется.

Потребители модели: DrinkWorkbench (все новые команды/лёгкие представления), drink_core_test/workbench_test (новая техника/сохранение), прежняя DrinkLab (старые сигнатуры, дополнительное поле игнорируется), GuestService/Session (прежняя печать/подача), ServiceGuest (необязательная техника/видимый лёд). Старые TEST-данные ядра и лаборатории не менялись; production-каталог добавляет test_water/test_soda и сосуды test_mixing_glass/test_shaker по 500 мл. Видимых бутылок семь, вода не выдаётся бутылкой. Полный журнал всё ещё ограничен MAX_COMMANDS, seal зарезервирован сверх лимита; смешивание/переливы не обходят печать/идемпотентность.

DrinkWorkbench владеет тремя отдельными DrinkPreparation: serving preparation, _mixing, _shaker. `get_container_snapshot(id: StringName) -> Dictionary`, `get_container_rect(id: StringName) -> Rect2` добавлены для профиля; ID cup/mixing/shaker. is_in_shaker теперь читает фактическое содержимое отдельного шейкера, прежний условный флаг убран. Подача затрагивает только preparation; замена пустого serving-сосуда не меняет остальные. Струя выбирает первое реальное пересечение края среди трёх сосудов, учитывает настоящий носик mixing. Переливы дозируются пакетами 0.1 с, смена цели/темпа/остановка/пауза сбрасывает уже налитое в модель. Это ограничивает журнал независимо от FPS. Промах/избыток извлекает реальные компоненты в DrinkSpillSurface, не списывая бутылки повторно. Кубик из ведёрка добавляет 30 мл ice-equivalent в выбранную тару; источник льда пока бесконечен TEST. При наливе из смесительной тары стрейнер встроен, отдельного управления ситом нет. Обновлены проверки старого условного whole-transfer пути на настоящие независимые/частичные состояния.

ServiceGuest.show_prepared сохраняет сигнатуру: при наличии technique.ice_ml показывает свежие кубики; при процеженной порции льда у гостя нет. Main/Session/ServicePanel, домашние API, preferences/checkpoint и формат сохранений не меняются.

## WORKBENCH-03: дополнение 2026-10-27

Новый `DrinkSpillSurface extends RefCounted`: `configure(catalog: DrinkMaterialCatalog) -> bool` однократно копирует цвета; `add_spill(components: Dictionary, point: Vector2) -> bool` атомарно проверяет известные материалы/положительные конечные объёмы/координаты, добавляет реальные компоненты и цвет по объёму. `advance(delta: float) -> void` растекает пятна на шаге <=0.05 с, соединяет касающиеся эллипсы; `get_patches() -> Array[Dictionary]` возвращает глубокую копию position/components/volume_ml/color/spread, статический radius задаёт тот же размер для UI и контактов. При объединении сохраняется сумма каждого компонента; более 64 пятен приближённо объединяются ближайшей парой. Потребители — DrinkWorkbench и workbench_test. Потери в слив не рисуются лужами; общий счёт пролива и расход бутылки сохраняют прежний смысл. Это поверхность тонких пятен, без отдельного отображения несмешивающихся фаз/уборки.

ServiceGuest добавляет `show_prepared(result: Dictionary, surface_position: Vector3) -> void`: доверенный снимок GuestService, шот/стакан и слои от реального состава, повторный render заменяет слои. Main вызывает после прежнего show_served и передаёт мировую точку верхней плоскости BarLevel/Geometry/CounterTop. Размеры сосуда и положение дна согласованы со столешницей и не зависят от rotation гостя. Старый show_served/legacy-контракт не меняется. Потребители — Main и профиль; сохранения/дом/временные события не расширяются.

## WORKBENCH-02: дополнение 2026-10-27

Новый `DrinkBottleStock extends RefCounted` — состояние одной бутылки каждого материала на смену, без зависимостей от UI/сохранений. `configure(catalog: DrinkMaterialCatalog, capacity_ml: float) -> bool` однократен; null/невалидный каталог и нечисловая/неположительная вместимость отклоняются. `get_remaining(id: StringName) -> float` возвращает 0 для неизвестного; `withdraw(id: StringName, requested_ml: float) -> float` отдаёт фактически извлечённое, ограниченное остатком, отрицательные/NaN/INF/неизвестные запросы не меняют состояние. Потребители: DrinkWorkbench и workbench_test. TEST-запас 500 мл при создании верстака, хранится в bottle_stock; новый сосуд не пересоздаёт модель запаса. Любой вышедший объём распределяется между порцией и проливом, при пустой бутылке струя прекращается.

DrinkWorkbench добавляет read-методы `get_bottle_remaining(id: StringName) -> float`, `get_bottle_angle(id: StringName) -> float`, `get_spill_patches() -> Array[Dictionary]` (глубокая копия position/volume_ml/color/spread) и шаг `advance_motion(delta: float) -> void`. _process вызывает motion перед pour; шаг ограничен 0.05 с, пружина делится на подшаги <=1/120 с. Движение курсора даёт импульс угловой скорости; фактический угол и скорость руки участвуют в расчёте струи. Пауза/resize/focus сбрасывают импульс и удержание, ни запас, ни состав не расходуются в фоне.

UI передаёт layered=true только при ложке у края, попадании рядом с ней, мягкой невысокой струе и спокойной бутылке. DrinkPreparation сохраняет общий API/правила фаз и не знает о ложке; лаборатория по-прежнему может явно запросить layered. Прямой налив смешивает совместимые материалы, несовместимые фазы остаются физическим исключением модели. Подбор реального предмета происходит до выбора новой посуды; порядок видимости/попаданий стакана согласован. Пролив получает локальную глубину поверхности из позиции руки, лужа хранит объём и растекается в плоскости. Это приближение 2.5D, не полная 3D-физика. Потребители методов верстака: собственный профиль; Main/Session/GuestService API и файлы дома не меняются.

## NarrativeSession

concurrent_service_enabled: bool=false — opt-in, Main задаёт free_roam_enabled до configure. Legacy по умолчанию прежний. `can_open_service() -> bool` — запрос доступности по режиму/configuration/served/времени, без мутации; намеренно не зависит от _changing, чтобы UI внутри mode_changed видел итоговую доступность. Команда open_service дополнительно проверяет _changing.

При opt-in open_service допускает DIALOGUE и сохраняет _service_return, не меняя Runner. close_service и успешная serve_drink возвращают в сохранённый режим. Menu/Journal скрывают оба экрана, возвращают точный прежний контекст; open_journal допускает SERVICE только при opt-in, ключ/страница/выбор речи не сбрасываются. choose_for_node/finish_for_node/cancel_dialogue по-прежнему принимают только DIALOGUE, в SERVICE отклоняются.

При активном Runner и готовых часах _has_service_time требует >=2 делений, иначе open_service/serve_drink отклоняются; проверка перед фактической подачей повторная. Вне разговора можно использовать последнее деление. Стоимости и ShiftClock API/схема прежние. Нулевое время не создаётся подачей посреди незавершённой реплики. configure_commute, режимы HOME/TRAVEL/Journal/Menu, сигналы и формат checkpoint не изменены.

## DRINK-CORE-01: независимый контракт приготовления

[DRINK_CORE](DRINK_CORE.md) фиксирует новые DrinkMaterialCatalog/DrinkPreparation, JSON материалов/сосудов, команды с идемпотентными ID и снимок результата. Текущие потребители — собственные тесты/TEST-стенд; Main/GuestService/дом не подключаются и прежние публичные интерфейсы не меняются. При дальнейшей интеграции рецепты/подача читают снимок, не изменяя порцию задним числом.
