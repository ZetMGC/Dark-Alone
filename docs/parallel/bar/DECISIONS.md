# DA-060: решения о параллельном обслуживании

## WORKBENCH-04: от условного шейкера к отдельным составам

2026-10-27, прямое поручение владельца изучить профессиональную практику и дать тару для независимой смеси с последующей укладкой слоем. Источники/факты и игровые приближения — BARTENDING_RESEARCH.md. Исправлено прежнее допущение: ложка помогает снизить энергию струи, но не является универсальным условием материала; сохраняем плотность всей смеси, ограничение темпа/высоты, даём малый допуск у стенки без ложки.

Каждый сосуд имеет свою DrinkPreparation. Перелив — проверенная передача фактических компонентов между двумя моделями с одним уникальным событием в каждой; часть остаётся у донора, жидкость не превращается в ID одного ингредиента. Смешанные дозы одного соотношения должны продлевать один слой, а не создавать множество полос от FPS. Сохранять состав, фазовую логику, технологию и атомарность при отказах. Пакеты 0.1 с ограничивают рост журнала; UI использует лёгкое представление без operations.

Stir/shake получают условную длительность обработки, лёд/реальную талую воду, температуру и аэрацию; работа без льда не создаёт холод/воду. Газированный TEST-компонент доливается/размешивается, не встряхивается. Лёд остаётся у источника через встроенный стрейнер, для подачи со льдом нужна отдельная порция в стакане. Подробные TEST-коэффициенты и ограничения не выдавать за измеренную физику; пассивные процессы, реальная хими́я/газообмен, измеритель и рецепты — последующие этапы. Все три черновика живут в памяти смены, checkpoint/Home не расширяются. Центральный ADR/реестры сводит координатор после ревью.

## WORKBENCH-03: общая физическая обратная связь и явная выдача

2026-10-27, отзыв владельца после WORKBENCH-02. Распространить пружинную инерцию на все перетаскиваемые инструменты; стоящие бутылки реагируют коротким импульсом вокруг дна, оставаясь на местах. Разрушения/полноценного rigid-body и нового звука не добавлять. Состав разлитого принадлежит отдельной DrinkSpillSurface, пятна объединяются по контакту с сохранением компонентов и объёма, цвет по объёму. Лимит 64 — только детализация, не удаление жидкости.

Проблема выбора посуды решается явными кнопками с текущим типом и сообщением при непустой порции; не терять напиток и не менять сосуд магически без перелива. Подносу дать отдельную крупную область, размещение лишь готовит порцию; передаёт кнопка «Подать гостю». Синхронный прежний service-event остаётся единственным списанием. Main показывает ту же смесь в соответствующем сосуде у гостя, привязывая дно к настоящей столешнице. Точка передаётся в мировых координатах, поскольку у гостя есть поворот. Файлы дома и общая схема сохранений независимы. При интеграции координатор сводит это дополнение в общий ADR/реестры и обновляет сценарий проверки подачи.

## WORKBENCH-02: физическая обратная связь и расход

2026-10-27, прямой отзыв владельца. Добавить угловую инерцию удерживаемой бутылки с затуханием и энергией движения курсора; фактический угол участвует в наливе. Струя промаха приземляется на локальную плоскость стола с растеканием, вместо постоянной нижней границы экрана. Для слоёв в игровом верстаке обязательна ложка, мягкая струя и верный порядок плотностей; общий модуль состава остаётся независим от предметов UI. Это согласованная игровая техника, не универсальное физическое ограничение. Начальный конечный запас по 500 мл — временный TEST-параметр; расходовать всё вышедшее, включая потери, показывать уровень на бутылке. Хранить в отдельной DrinkBottleStock, не расширять checkpoint/склад. Исправить первопричину недоступного стакана: реальные предметы раньше rack hit-зон, видимость стакана соответствует приоритету выбора. Точное количество запасов и реалистичное пополнение потребуют отдельного дизайна. Крупных зависимостей/изменений дома нет.

## WORKBENCH-01: свободная поверхность вместо списка

2026-10-27, вариант 2 выбран владельцем и отдельно подтверждён. В обычном free-roam приготовление становится 2D-поверхностью с перетаскиваемой посудой/бутылками/инструментами. Настоящая задняя 3D-стойка получает коврик, посуду, бутылки, инструменты и слив без изменения проходимости/WorkPosition. UI передаёт в уже существующую модель фактические дозы, а не ID готового рецепта; GuestService запечатывает саму модель и сохраняет прежнее одноразовое событие времени. Legacy меню остаётся opt-out для совместимости.

Речь занимает верхний правый угол и продолжает набор, ответы блокируются прежним правилом рабочего ракурса. Пауза/выход сохраняют черновик в памяти текущей смены и прекращают удержание, чтобы возврат не начинал налив/подачу сам. Сохранения между запусками не расширяются. Первая версия шейкера перемещает одну порцию целиком; независимые объёмы нескольких сосудов — отдельное расширение, не скрытая гарантия этого UI. Материалы TEST; рецепты/реакции не подменяются декоративными результатами. При интеграции координатор переносит это решение в общий ADR и подключает новый профиль проверок; домашняя дорожка независима.

Дата 2026-10-27, локальная запись решения барной дорожки. При интеграции координатор перенесёт в общий ADR. Основание — задача владельца DA-060, уточняет ADR-0025 без изменения HOME-контрактов.

Сохраняем прежние режимы NarrativeSession. Новый opt-in concurrent_service_enabled=false включается Main только для free-roam бара. SERVICE хранит _service_return (exploration/dialogue), Runner остаётся активным. Bubble виден и набирается в SERVICE, но пассивен; у задней стойки DIALOGUE также пассивен. Цифры/колесо/F/Backspace не перехватываются пассивным пузырьком. Чтобы ответить/продолжить длинную реплику, закрыть выбор и отойти Escape, затем посмотреть на NPC. UI не является хранилищем состояния.

Фокус допускается в DIALOGUE через E по задней поверхности; камера неподвижна, курсор свободен. Первоначальный старт разговора из фокуса по-прежнему освобождает ходьбу; возврат из SERVICE/Menu/Journal больше не освобождает рабочее место самовольно. Открытие/закрытие выбора сохраняет страницу/набор/выбор реплики. Menu/Journal скрывают оба интерфейса и ставят набор/тело на паузу, возврат восстанавливает SERVICE или DIALOGUE.

Сохраняем стоимость 1 за завершённый разговор и 1 за подачу, без отсроченного/отрицательного списания. При активном Runner подача разрешена только при remaining >= 2: одно деление должно оставаться для окончания разговора. При remaining == 1 выбор/подача отклоняются с объяснением, реплика остаётся активной; сначала закончить/отменить разговор. Это проверка доступности, не предварительное списание времени. При нормальной подаче из 2 остаётся 1 и диалог продолжается; его завершение даёт 0 и итоги. Тот же барьер повторяется перед serve_drink, включая изменение времени после открытия меню. ShiftClock/schema не меняются. Legacy по умолчанию сохраняет прежнее взаимоисключение экранов.

Меню напитков при активном разговоре компактное внизу справа, пузырёк выше, без полноэкранного затемнения. Новых рецептов/канона/жидкости/рук нет. Home, checkpoint и preferences не расширяются.

## DRINK-CORE-01: состав отдельно от сцены и эффектов

2026-10-27, утверждённое направление владельца из DRINKS_PLAN, первый этап. Налив/смеси/слои реализуются отдельной детерминированной моделью. Все численные коэффициенты плотности/темпа/вязкости условные TEST, без полной физики жидкости. Разные группы смешивания дают отдельные фазы, shake — эмульсию до явного settle; совместимые слои не сохраняются после перемешивания. Порция хранит фактический состав и технологию, а не ID правильного рецепта. Неудачная команда атомарна, успешная уникальна по ID; seal выдаёт независимый финальный результат и закрывает изменения. Внешний владелец обеспечивает уникальные ID порций. Это позволяет позднее отдельно распознавать рецепты/реакции без зависимости от мешей/UI/дома. Подробные формулы/границы — DRINK_CORE.md. Схемы checkpoint/GuestService/Session не меняются.
